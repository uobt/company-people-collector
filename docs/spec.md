# Спецификация и ТЗ: поиск LinkedIn компании и профилей сотрудников

**Статус:** задание на разработку, не описание уже работающего парсера.  
**Входной пример:** `https://dedicateddevelopers.com/`.  
**Целевой результат:** для каждой компании — ссылка на её подтверждённую страницу LinkedIn и список записей «ссылка на профиль человека + отображаемое полное имя», с источником, временем наблюдения и честным статусом покрытия.

## 1. Задача и границы

Сделать локальное приложение с интерфейсом командной строки для пакетной обработки сайтов компаний. Оно находит официальную страницу компании в LinkedIn, затем **через заранее разрешённый канал получения данных о людях** извлекает доступные профили, связанные с этой компанией. Каждая запись содержит URL персонального профиля и полное имя в написании источника. Обрабатывать только деловой контекст; помимо имени и URL не собирать email, телефоны, другие личные сведения, фотографии, связи, сообщения и историю профилей; не отправлять приглашения или сообщения.

**Важное условие реализуемости:** ссылка на страницу компании не даёт права или технической возможности автоматически выгрузить список её сотрудников. Прямой обход LinkedIn, включая раздел «Сотрудники», **не включается в работающий режим по умолчанию**. Перед разработкой/включением соответствующего коннектора исполнитель должен проверить и документально подтвердить, что выбранный канал разрешает именно автоматическое получение, хранение и экспорт **имён и ссылок на профили третьих лиц** в нужном объёме. Если такого канала нет, готовым результатом первой версии остаются обнаружение LinkedIn-страницы компании и импорт уже правомерно полученных данных; статус сотрудников — `source_unavailable`, а не фиктивный успех. Нельзя выдавать импорт за прямой парсер LinkedIn.

Публичная видимость страницы, наличие `?trk=org-employees`, успешный ответ HTTP, подписка на сторонний сервис или доступ из пользовательского аккаунта сами по себе не подтверждают разрешение на массовый сбор. Не проектировать обход логина, CAPTCHA, 403/429, внутренних API, маскировку браузера, ротацию прокси/аккаунтов, перенос cookies и покупку данных с неясным происхождением.

## 2. Проверка доступа до сетевой реализации

Исполнитель составляет `docs/access_assessment.md` по каждому источнику (сайт компании, LinkedIn, лицензированный поставщик): дата проверки, URL условий и robots.txt, конкретный разрешённый тип доступа, разрешение на нужные поля/экспорт, лимиты, срок хранения, требуемые договоры, фактический ответ из среды запуска и решение `allowed | blocked | unknown`. Robots.txt и пользовательское соглашение проверять **раздельно**: robots.txt не заменяет условия использования, а его недоступность не трактуется как разрешение. При `blocked`/`unknown` не запускать соответствующий live-коннектор.

Для LinkedIn проверить действующее [Пользовательское соглашение](https://www.linkedin.com/legal/user-agreement) и [краткое изложение](https://www.linkedin.com/legal/user-agreement-summary), а также условия выбранного официального либо лицензированного канала. В соглашении предусмотрены ограничения доступа и доступности функций; конкретное разрешение на массовое извлечение персональных профилей **не следует предполагать**. Решение о правомерности обработки персональных данных для используемых стран и целей (основание, информирование, срок хранения, удаление) принимает владелец данных/юрист, а не парсер.

Допустимые варианты второй стадии при подтверждённых правах:

1. Документированный API или экспорт по договору, **явно** предоставляющий сведения о людях, связанных с компанией, и право хранить/экспортировать требуемые поля. Название продукта или API и конкретный метод фиксировать только после проверки документации и пилота.
2. Файл CSV/JSONL от владельца данных или поставщика, предоставленный с подтверждением прав на эти поля и такое использование.
3. Другой разрешённый источник с явной связью «компания — человек» и профильной ссылкой; в результате помечать фактический источник, не обозначать такую запись как прочитанную из LinkedIn.

Не предполагать существование открытого LinkedIn API для выгрузки сотрудников произвольной компании. Ни один вариант не должен автоматически обходить запрет сайта или условия источника. Платный API/подписку подключать лишь после согласования цены и лимитов.

**Пилот после допуска:** один согласованный сайт, до 5 страниц сайта компании, до 1 подтверждённой страницы компании и до 20 записей людей из разрешённого канала. Сохранить в отчёте реальные поля, схему пагинации, критерий окончания, ошибки и покрытие. Не фиксировать селекторы, эндпоинты, «все сотрудники» и конкретные ограничения поставщика по догадке до этого пилота.

## 3. Вход, управление запуском и выход

### 3.1. Вход

CSV UTF-8 или JSONL; одна компания на строку. Обязателен `website_url` (например, `https://dedicateddevelopers.com/`); необязательны `company_name`, `country`, `company_linkedin_url` (подсказка, требующая проверки). При дублях нормализованного домена объединять задания, сохраняя исходные строки и выдавая отчёт о дублях. Несколько брендов на одном домене или несколько LinkedIn-страниц не объединять автоматически без подтверждения.

Пример команды (проектный интерфейс, не запущенная программа):

```text
company-people doctor --config config.yaml
company-people discover --input companies.csv --output companies.jsonl
company-people import-people --input licensed_people.csv --source approved_vendor
company-people collect --input companies.csv --source approved_vendor --live
company-people export --format csv --output people.csv
```

`collect --live` доступен только при записанном допуске именно для этого источника/набора полей и явном выборе разрешённого коннектора. `doctor` лишь показывает доступность и основания, но не выдаёт разрешение автоматически по HTTP 200. `--dry-run`, `--max-sites`, `--max-pages-per-site`, `--max-people-per-company`, `--max-requests`, `--resume RUN_ID` обязательны. Защитные дефолты: до 5 страниц сайта, до 100 людей на компанию (технический предел, **не** утверждение о полноте), до 100 запросов за запуск; реальные лимиты источника имеют приоритет.

### 3.2. Основной экспорт `people.csv`

Одна строка = один **наблюдённый** человек в одной компании; заголовки и порядок:

```csv
input_website_url,company_linkedin_url,profile_url,full_name,source_url,source_type,affiliation_evidence,observed_at,confidence
```

- `input_website_url` — исходный сайт из входа; `company_linkedin_url` — проверенная каноническая ссылка на страницу компании или пусто.
- `profile_url` — абсолютная ссылка вида `https://<разрешённый-домен-linkedin>/in/<slug>/`; допустимы локализованные хосты (`www.linkedin.com`, `co.linkedin.com` и т. п.) после проверки принадлежащего LinkedIn домена. Исключить `/company/`, `/posts/`, рекламу и чужие домены; не формировать URL из имени.
- `full_name` — отображаемое имя как в источнике, Unicode, без сокращения и транслитерации. Если есть только инициалы/скрытое имя — не создавать валидную строку, сохранить причину пропуска в отчёте. Не делить автоматически на `first_name`/`last_name`: многокомпонентные имена не обязаны укладываться в две части.
- `source_url`, `source_type` (`licensed_api | licensed_file | company_site | permitted_linkedin`), `affiliation_evidence` — откуда взяты имя, URL и основание связи с компанией; если источник не позволяет точный URL документа, указать идентификатор записи в отдельном служебном поле JSONL. `confidence` = `high | medium | review`; отсутствие явной текущей связи с компанией → `review`, не утверждать «сотрудник».
- `observed_at` — момент получения UTC ISO 8601, не дата начала работы в компании.

Для компактного человекочитаемого вывода поддержать `--format pairs`: `profile_url, full_name; profile_url, full_name`. Машиночитаемый канонический экспорт — CSV/JSONL, поскольку имя или URL могут содержать запятые и неоднозначную пунктуацию. Если нужны буквально исходные URL пользователя с `?trk=org-employees`, вести отдельное `profile_url_raw`, но **в основном поле удалять трекинговые параметры**; они не требуются для идентификации и не доказывают происхождение записи.

### 3.3. Отдельный экспорт `companies.jsonl`

Для **каждой** строки входа, включая нулевой результат, сохранить `input_website_url`, `company_name`, `company_linkedin_url|null`, `company_linkedin_source_url|null`, `discovery_status`, `people_status`, `people_count`, `pagination_exhausted` (`true | false | null`), `coverage_note`, `stop_reason`, `observed_at`, `run_id`. Статусы обнаружения: `found | ambiguous | not_found | site_blocked | error`; статусы людей: `complete_available_pages | partial | source_unavailable | blocked | no_people_observed | not_attempted | error`. `complete_available_pages` означает только конец **разрешённой доступной выдачи**, а не всех фактических сотрудников. Пустой `people.csv` без этого отчёта не считается успешной обработкой.

## 4. Алгоритм

### Шаг A. Поиск страницы компании

1. Проверить входной URL: разрешить только `https`/`http`, запретить адреса локальной сети, localhost, link-local, нестандартные порты, учетные данные в URL и уход редиректом на запрещённый адрес (защита от SSRF). Не брать корпоративное имя из домена как доказанный факт.
2. С учётом правил и лимитов сайта посетить главную и явно связанные страницы `about`, `contact`, `team`, видимые ссылки в шапке/подвале; `sitemap.xml` использовать, только если допустим и полезен. Не перебирать бесконечно шаблонные пути, не уходить с домена без проверки. Параметры URL и фрагменты для обхода нормализовать.
3. Извлечь ссылки на `linkedin.com/company/<slug>/` и возможные варианты страницы компании; учесть относительные ссылки, редиректы социального виджета и экранирование HTML. Ссылки на `/in/` — ссылки людей, **не** кандидаты на страницу компании. LinkedIn-иконка, ведущая на личный профиль, не становится страницей компании.
4. При нескольких кандидатах сопоставить подтверждённое имя, домен и явный контекст ссылки; при отсутствии однозначного подтверждения — `ambiguous` с кандидатами. Если доступ к LinkedIn допустим, сверить заявленный там официальный домен; если недопустим, не выдавать непроверенное сопоставление за факт. Поисковая система/сторонняя выдача — только отдельно разрешённый дополнительный канал с зафиксированными условиями, не способ обойти блокировку LinkedIn.
5. Записать `company_linkedin_source_url` как страницу сайта, содержащую ссылку, либо проверенное основание из разрешённого источника; отсутствие ссылки → `not_found`, а не придуманный slug.

### Шаг B. Получение людей (только для допущенного канала)

1. Запросить записи по подтверждённому идентификатору компании; использовать **документированные** параметры, пагинацию и поля выбранного канала. Не использовать скрытые внутренние endpoint'ы LinkedIn.
2. Для каждой записи принимать пару только тогда, когда источник действительно даёт имя и ссылку на профиль одного человека и есть явное подтверждение принадлежности к этой компании в нужном контексте. Различать `current_confirmed`, `listed_without_current_status`, `former` и `unclear` в `affiliation_evidence`; по умолчанию экспортировать как сотрудника лишь `current_confirmed`, остальные — отдельный файл `review.jsonl` или режим с явным флагом.
3. Валидировать URL по разбитому хосту и пути (не проверкой подстроки `linkedin.com`), отбрасывать посторонние пути, пустые имена и служебные карточки. Текст имени брать из явного поля/подписи, **не** из slug, аватара или совпадения со сниппетом поисковика.
4. Канонизировать ссылку для дедупликации: нормализовать хост и схему, удалить фрагмент, трекинговые параметры (`trk`, `originalSubdomain` и подобные при доказанной нерелевантности), сохранить идентифицирующий путь и исходный URL в служебном поле. Не склеивать разные slug лишь по совпадению имён; профиль одного человека, видимый в нескольких компаниях, — две связи «компания — профиль», но один нормализованный профиль.
5. Останавливать выдачу по фактическому концу документированной пагинации либо лимиту. На лимите/недоступной странице писать `partial`, `pagination_exhausted=false/null` и причину; не объявлять список полным.

### Шаг C. Хранение и возобновление

SQLite: `runs`, `companies`, `company_candidates`, `people`, `company_people`, `observations`, `source_access`. Отдельные ключи: нормализованный домен/сайт компании, канонический URL страницы компании и канонический URL профиля; связь хранит доказательство и дату наблюдения. Сохранять как минимум ссылки на источник, минимум диагностик и хеш/идентификатор разрешённого ответа; не архивировать целые страницы с лишними персональными данными без отдельного основания. Повторный запуск обновляет наблюдения, не стирая историю ошибок и происхождение записи. Появление/исчезновение в выдаче **не** означает трудоустройство/увольнение. Нужны удаление данных по запросу, заданный оператором срок хранения и журнал доступа к экспорту.

## 5. Надёжность и безопасность

- Отдельные модули для обхода сайта компании, проверки ссылки, коннектора разрешённого источника людей, чистого разбора ответов, нормализации, SQLite и экспорта. Парсер сохранённого документа тестируется без сети.
- Для каждого домена — ограничение частоты, последовательные запросы по умолчанию, таймауты и конечное число повторов на временных 5xx/сетевых ошибках; при 429 учитывать `Retry-After`, затем останавливаться. При 401/403/challenge/auth-wall — `blocked`, без попыток обхода. Числа в конфигурации — защитные ограничения, не разрешённая площадкой квота.
- Проверять актуальные условия и robots.txt целевых сайтов перед live-запуском, журналировать URL/время/HTTP-статус/причину остановки без токенов и содержимого личных профилей. Токены разрешённого API хранить в защищённом окружении, не в коде или экспорте.
- CSV UTF-8 с BOM для открытия в Excel, корректное экранирование кавычек/запятых/переносов; нейтрализовать формулы в текстовых полях при CSV-экспорте. JSONL — UTF-8 и исходные Unicode-имена. Вести счётчики: компаний всего, найденных/неоднозначных LinkedIn-страниц, записей людей, отброшенных/на проверку, блокировок и частичных результатов.
- Персональные данные обрабатывать по принципу минимизации: контроль доступа к файлам, понятная цель, срок хранения, механизм удаления; автоматическая рассылка и обогащение личными контактами не входят в проект.

## 6. Приёмка и тестовые сценарии

### 6.1. Пример, предоставленный заказчиком

> **Примечание публичной версии:** имена и ссылки профилей в примере заменены на фиктивные (`example-co`); сохранены формат, трекинг-параметры и локализованный хост.

Следующие пары — **контрольный ожидаемый вывод на учебном снимке/разрешённом импорте**, а не утверждение, что эти люди сейчас работают в компании или что их профили проверены во время написания ТЗ:

| Вход | Профиль из примера | Полное имя из примера |
|---|---|---|
| `https://dedicateddevelopers.com/` | `https://www.linkedin.com/in/avery-stone-example-co?trk=org-employees` | Avery Stone |
| тот же | `https://www.linkedin.com/in/jordan-vale-94844727?trk=org-employees` | Jordan Vale |
| тот же | `https://www.linkedin.com/in/riley-example-co?trk=org-employees` | Riley Quinn |
| тот же | `https://co.linkedin.com/in/casey-north?trk=org-employees` | Casey North |

На тестовом импорте с четырьмя разрешёнными записями нормализация создаёт **ровно четыре** пары в порядке источника, если он известен; в `profile_url` нет `?trk=org-employees`, в `profile_url_raw` он сохранён. Локализованный хост `co.linkedin.com` принимается без принудительной замены на `www.linkedin.com`. Сопоставление имён со slug не используется. При наличии подтверждения актуальной связи эти четыре пары попадают в `people.csv`; если учебный импорт его не содержит, они попадают в `review.jsonl` и **не выдаются** за проверенных текущих сотрудников. Компания и статус в `companies.jsonl` отражают фактический путь получения; тестовый импорт не маркируется как live-сбор LinkedIn.

### 6.2. Обязательные проверки

1. Сайт содержит одну подтверждаемую ссылку `/company/` → найденная страница компании и URL страницы сайта в происхождении; ссылки только на `/in/` → страница компании не найдена.
2. Две LinkedIn-страницы дочерних брендов без однозначного совпадения → `ambiguous`, без автоматического выбора.
3. Одно имя без URL, один URL без имени, одноимённые разные люди, один профиль с `trk`/без `trk`, локализованный LinkedIn-хост, имя с диакритикой/многокомпонентным написанием → корректный отбор и дедупликация, без придуманных имён.
4. Бывший сотрудник или отсутствие доказательства текущей связи → не попадает в подтверждённый список; файл проверки сохраняет исходный источник и причину.
5. Блокировка источника, отсутствие права на доступ, CAPTCHA или 403 → нет обхода, явный `blocked`/`source_unavailable`, без фиктивных строк; 429 → уважение ограничения и `partial`, если выдача оборвана.
6. Прерывание и `--resume` → не дублирует людей; принудительный лимит → честный `partial`; повторный импорт одинакового файла → идемпотентность наблюдений по ключу источника и записи.
7. SSRF-тесты для `localhost`, приватных IP и редиректов на них; CSV-тест на кавычки, переносы, `=SUM(...)` в имени; тест удаления записей по запросу.

**Критерий приёмки стадии 1:** CLI, офлайн-тесты, обнаружение страниц компаний на разрешённых сайтах, корректные CSV/JSONL и статусы без выдуманной полноты.  
**Критерий приёмки стадии 2:** положительный `access_assessment.md` для конкретного канала, live-пилот с воспроизводимыми артефактами и согласованными лимитами, затем воспроизводимый end-to-end запуск с явно указанным уровнем покрытия. ## 7. Состав поставки и порядок разработки
